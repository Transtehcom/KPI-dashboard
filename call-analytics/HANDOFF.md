# Аналитика звонков: передача контекста

Контекст из чата с Claude (20.10.2026). Прочитай целиком перед началом работы.

## Цель

Автоматическая расшифровка и аналитика телефонных переговоров для контроля качества и связи с мотивацией.
Встраиваем в существующий KPI-дашборд (этот репозиторий), **новый дашборд не делаем**.

| # | Задача | Критерий приёмки |
|---|---|---|
| 1 | Интеграция с телефонией: сохранение записей звонков в хранилище | Записи сохраняются и доступны по карточке сделки/сотрудника |
| 2 | Расшифровка и базовый NLP: цены, сроки, возражения, тональность | Точность ключевых полей >80% на тестовой выборке; расшифровка доступна в карточке записи |
| 3 | Дашборды и сводки по звонкам, метрики для мотивации (кол-во предложений, успешных договорённостей и пр.), ручное прослушивание | Отчёты по периодам; менеджер видит свой KPI и по каким звонкам он не достигает цели |
| 4 | Права на прослушивание и приватность (лог прослушиваний) | Слушать могут только уполномоченные; лог доступен администратору |

## Принятые решения

- **Распознавание речи только локально**, на офисном компьютере, где работает дашборд. Запись не уходит в облако.
  Модель GigaAM v2 (Сбер, русский язык) через `sherpa-onnx`, скрипт `call-analytics/transcribe.py`
  (флаг `--fast` = только GigaAM). Замер на 2 ядрах: минутный звонок ~33 с, ~600 МБ RAM в режиме `--fast`;
  с Whisper turbo ~3 мин и ~2 ГБ. Модели скачиваются с GitHub-релизов k2-fsa/sherpa-onnx в `~/.cache/call-transcribe`.
- **Обезличивание до передачи текста в Claude**: телефоны/email/ИНН регулярками, ФИО/организации/адреса через Natasha,
  замена на метки `[ИМЯ_1]`, `[ОРГ_2]`; таблица замен хранится только локально; после ответа Claude — обратная подстановка.
  Это псевдонимизация по 152-ФЗ (для нас данные остаются ПДн, получатель не может установить личность).
- **Claude для NLP** вызывается в фоне (`claude -p`) по обезличенному тексту, возвращает структурированный JSON
  (цены, сроки, возражения, тональность, договорённости, следующий шаг). Расход идёт из лимита подписки:
  проверить, хватает ли его на реальный поток звонков.
- Опционально, запись обратно в Б24: итог звонка комментарием в таймлайн (`crm.timeline.comment.add`),
  полная расшифровка к звонку (`telephony.call.attachTranscription`: реплики User/Client с таймкодами).

## Что выяснено о текущем коде

- `app/bitrix24.py` → `fetch()` уже вызывает `voximplant.statistic.get`, но:
  - фильтр `CALL_TYPE: 1` берёт только **исходящие** звонки;
  - сохраняются только длительность, ЛПР/секретарь, следующий шаг, клиент; **`CALL_ID`, `CALL_RECORD_URL`,
    `RECORD_DURATION`, `CRM_ACTIVITY_ID` отбрасываются**;
  - таблица `activities` (`app/common.py`, SCHEMA) полностью перезаписывается при синхронизации (`SYNC_TABLES`),
    поэтому данные записей и расшифровок нужно хранить в **отдельных таблицах, которые синхронизация не трёт**
    (по аналогии с `manual_fields` и `lead_qualified`).
- Права: `role == "manager"` видит всех, сотрудник только себя (проверяет сервер, `app/server.py`); есть флаг admin.
  Журнала действий пользователей нет.
- `data/dashboard.err.log`: таймаут SSL handshake к Б24 именно на `voximplant.statistic.get`. В `call()` стоит добавить
  повтор с паузой (запросов станет больше из-за скачивания записей).
- Телефония внешняя (в именах файлов записей `ttk711_...`); в статистике такие звонки идут с `CALL_CATEGORY: external`.
  **Не проверено**: скачивается ли запись по `CALL_RECORD_URL` напрямую или нужен `disk.file.get` по `RECORD_FILE_ID`.
  Проверить первым делом на реальном портале.
- Пример имени файла записи: `ttk711_out_79370090994_2026_10_13-09_41_44.mp3` (направление, номер, дата-время), 8 кГц моно.

## Сделано: п.1 плана (записи), 20.10.2026

- Проверено на портале: запись скачивается и с Диска Б24 (`disk.file.get` по `RECORD_FILE_ID` → `DOWNLOAD_URL`, mp3),
  и напрямую с АТС по `CALL_RECORD_URL` (МегаФон ВАТС, без авторизации). Берём с Диска Б24, ссылка АТС — запасной путь.
  У ~12% звонков записи нет. `RECORD_DURATION` не заполняется — длительность берём из `CALL_DURATION`.
  В статистике есть `TRANSCRIPT_ID` / `TRANSCRIPT_PENDING` (расшифровка Б24) — у нас не используется.
- Звонок в статистике привязан к контакту/компании/лиду; к сделкам — через привязки своего дела
  (`crm.activity.binding.list`). Звонок по компании бывает привязан сразу ко всем её сделкам (в примере — к 8).
- `fetch()` берёт входящие и исходящие; в `activities` входящие идут с `direction="in"`, KPI считает только `out`.
- `app/call_records.py`, таблица `call_records` (не в `SYNC_TABLES`, id = `call<ID>` как в `activities`):
  upsert при синхронизации, затем в фоне — привязки (пакетом `batch`), скачивание (новые первыми,
  `max_per_run` за проход), удаление аудио старше `keep_days`. Выборка для интерфейса — `listing()` (по сотруднику, периоду, сделке).
  Настройки — секция `call_records` в `config.json` (см. `config.example.json`), по умолчанию `data/records`, бессрочно.
- `Bitrix24.call()` повторяет запрос при сетевых сбоях (таймаут SSL и т.п.), добавлен `Bitrix24.batch()`.
- Прогон на портале во временную базу: за 2 дня 46 звонков с записью у 7 сотрудников, в среднем ~300 КБ на запись
  (оценка ~25 записей/день, ~2,7 ГБ в год). Первая выгрузка за 6 месяцев (~4500 файлов) займёт ~15 синхронизаций.

## Сделано: п.2 плана (права и журнал), 20.10.2026

- Вкладка «Звонки» (`web/index.html`, `renderCalls`): звонки с записью за месяц, поиск по ID сделки Б24, ссылки на сделки,
  плеер. Плеер создаётся только по нажатию «Слушать» — иначе браузер заранее качал бы записи и они попадали бы в журнал.
- `GET /api/calls` — сотрудник видит только свои звонки (параметр login игнорируется), администратор — любого
  сотрудника, всех или по сделке; администратору — сколько раз прослушан звонок.
- `GET /api/call-audio?id=` — аудио только через сервер, права проверяются на каждый запрос (`call_records.can_listen`):
  администратор (`role == manager`) — любые, сотрудник — свои (`call_records.listen_own`, по умолчанию true),
  руководитель отдела с правом `listen_dept` — ещё звонки своего отдела.
  Поддерживается Range (перемотка). Отдаётся без общей блокировки базы.
- Таблица `listen_log` (ts, login, record, emp, ip, result). Пишется начало воспроизведения (без Range или с `bytes=0-`),
  повтор той же записи тем же человеком в течение 10 минут — одно прослушивание; перемотка не пишется.
  Запрос чужой записи без прав — 403 и строка `denied`.
- Право «Слушает звонки своего отдела» (`employees.listen_dept`, галочка в карточке сотрудника): записи коллег
  с тем же полем «Отдел»; без доступа к их KPI и к журналу. Список доступных — `call_records.audible_logins()`.
- `GET /api/listen-log` — только администратору; в интерфейсе — «Журнал прослушиваний» под списком звонков (по умолчанию 30 дней).
- Проверено тестами (`tests/test_listen.py`, настоящий HTTP-сервер) и в браузере на копии базы с реальными записями.

## п.3 плана (расшифровка): сделано 20.10.2026

- Установлено на ttk1025: sherpa-onnx, soundfile, numpy, scipy, natasha, pymorphy3 (+словари); модели GigaAM v2,
  silero VAD, Whisper turbo — в `~/.cache/call-transcribe`. Claude Code CLI: `C:\Users\BartovKK\.local\bin\claude.exe`
  (не в PATH, вызывать по полному пути), вход выполнен: claude.ai, подписка **Pro**.
- Замер на i3-12100 (10 реальных звонков, 31 мин аудио): `--fast` (GigaAM) — **5,2 с на минуту звонка**;
  полный режим с Whisper — ~35 с на минуту, пик памяти ~2,1 ГБ. Выбран **быстрый режим**: GigaAM пишет почти все
  слова, Whisper ставит пунктуацию, но теряет куски фраз и иногда выдумывает.
- Записи моно: реплики менеджера и клиента не разделены — Claude будет определять по смыслу.
- `app/transcripts.py`, таблица `call_transcripts`: после скачивания записей фоновый проход запускает
  `transcribe.py --jsonl --fast` отдельным процессом с пониженным приоритетом, не больше `transcribe_per_run` (200)
  записей за раз, новые первыми; 3 попытки на запись. Голосовое меню АТС вырезается (`IVR_PHRASES`,
  дополняется `call_records.ivr_phrases`). Расшифровка удаляется вместе с аудио по сроку хранения.
- Вкладка «Звонки»: кнопка «Текст» (те же права, что на прослушивание; в журнал — `read`), щелчок по таймкоду —
  слушать с этого места.
- Обезличивание (следующий шаг): natasha на тексте без заглавных букв имена не находит — основной способ pymorphy3
  (теги Name/Surn/Patr/Geox/Orgn) + известные из CRM клиенты и контакты + регулярки (телефон, email, ИНН).
- Вызов Claude: `claude.exe -p --output-format json --model sonnet --no-session-persistence --system-prompt … --tools ""
  --strict-mcp-config --setting-sources "" --disable-slash-commands` из пустой папки — ~1 тыс. токенов служебной
  части вместо ~39 тыс. со стандартной (`--bare` не подходит: только API-ключ). Пустые аргументы передавать
  из Python, не из PowerShell 5.1 (теряет "").

4. **Метрики (п.3).** Новые показатели в `kpi_rules.json` (справочно или как пункты KPI), в карточке пункта —
